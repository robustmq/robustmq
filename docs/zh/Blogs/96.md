# mq9 承载 A2A：一些设计思考

## 核心抽象：mailbox

mq9 的核心抽象只有一个——mailbox。

mailbox 是轻量的、可丢弃的通信资源。Agent 想通信就申请 mailbox，用完就废弃，不需要管理 session 生命周期。这是 unix 的"everything is a file"哲学的 mq9 版本——everything is a mailbox。

## mail_address 格式规范

mail_address 是 mailbox 的唯一标识，命名规则要严格。

**字符集：** 小写字母 (a-z)、数字 (0-9)、点 (.)

**长度：** 1 到 128 字符

**大小写：** 严格小写，包含大写字符的 mail_address 会被 broker 拒绝

**位置规则：** `.` 只能出现在中间，开头和结尾必须是小写字母或数字；不允许连续的 `.`

**语义：** 不透明字符串，`.` 不参与协议路由或匹配

**编码：** 不允许 URL percent-encoding

合法示例：`task.001`、`agent.inbox`、`analytics.result`、`acme.org.task.queue`

非法示例：`task-001`（含连字符）、`Task.001`（含大写）、`task..001`（连续点）、`.task.001`（点开头）

## URI Scheme：mq9:// 和 mq9s://

mq9 用标准 URI 形式表达 mailbox 地址：

```
mq9://host[:port]/{mail_address}    # 明文
mq9s://host[:port]/{mail_address}   # TLS 加密
```

完整示例：

```
mq9://127.0.0.1:4332/task.001
mq9://broker.example.com/agent.inbox
mq9s://broker.example.com:4332/analytics.result
mq9s://mq9.acme.org/acme.task.queue
mq9://127.0.0.1:4332/session.20260502
mq9s://broker.example.com/order.processing.urgent
mq9s://broker-east-1.acme.org:9332/agent.001.inbox
```

这个设计的关键价值：**A2A 协议一行不用改**。A2A 的 `pushNotification.url` 字段定义就是个 URL，HTTP webhook 是 `https://...`，mq9 mailbox 是 `mq9://...`。从协议层看是同一个字段，从实现层看是两套传输。SDK 拿到 URL 后做协议分发即可。

A2A 工作组什么都不用做，他们的协议本来就允许任何 URL scheme。这是利用了协议留下的扩展空间，不是改协议。

## 协议总览

```
Mailbox 管理：
  $mq9.AI.MAILBOX.CREATE                                 创建 mailbox

消息通信：
  $mq9.AI.MSG.SEND.{mail_address}                        发送消息（normal 优先级）
  $mq9.AI.MSG.SEND.{mail_address}.urgent                 发送消息（urgent 优先级）
  $mq9.AI.MSG.SEND.{mail_address}.critical               发送消息（critical 优先级）
  $mq9.AI.MSG.SUB.{mail_address}                         订阅 mailbox 消息
  $mq9.AI.MSG.ACK.{mail_address}.{msg_id}                订阅 ACK 消息
  $mq9.AI.MSG.QUERY.{mail_address}                       查询 mailbox 内消息
  $mq9.AI.MSG.DELETE.{mail_address}.{msg_id}             删除指定消息

Agent 管理：
  $mq9.AI.AGENT.REGISTER                                 Agent 注册
  $mq9.AI.AGENT.UNREGISTER                               Agent 注销
  $mq9.AI.AGENT.REPORT                                   Agent 状态上报
  $mq9.AI.AGENT.DISCOVER                                 Agent 发现
```

## Agent 注册和发现

**mq9 注册中心和传统注册中心的根本区别：**

传统注册中心（etcd、Consul、Nacos）回答的问题是"服务在哪里"——IP:Port、健康检查、负载均衡。服务的内容对它们透明，不关心。

mq9 注册中心回答的问题是"谁能做这件事"——注册的是 A2A AgentCard，包含能力描述、skills、tags。发现即能力匹配，不是地址查询。这是专门为 Agent 生态设计的，传统注册中心没有这个概念。

**注册：Body 是上层协议的内容（当前示例为 A2A AgentCard），mq9 不干涉，以后换其他协议同理。mq9 只要求 Body 中携带 `mailbox` 字段作为路由标识。**

```
# 注册（Body 是协议内容，mq9 不干涉）
nats request '$mq9.AI.AGENT.REGISTER' \
  '{ ...AgentCard，mailbox = "mq9://broker/agent.translator.inbox"... }'

# 发现（按 tag 检索，返回原始注册内容列表，mq9 不转换不包装）
nats request '$mq9.AI.AGENT.DISCOVER' '{"tag": "translate"}'
# 返回：[{ ...原始注册内容... }, ...]

# 状态上报（Body 是协议内容，mq9 不干涉）
nats request '$mq9.AI.AGENT.REPORT' \
  '{ ...mailbox = "mq9://broker/agent.translator.inbox", 状态字段由上层协议定义... }'

# 注销
nats request '$mq9.AI.AGENT.UNREGISTER' \
  '{ ...mailbox = "mq9://broker/agent.translator.inbox"... }'
```

**DISCOVER 的演进路线：**

mq9 对注册内容不做 schema 约束，但可以从 Body 中提取 `mailbox`、`skills.tags` 等公认字段建索引，DISCOVER 能力随之增强：

- **当前（tag 检索）**：按注册时携带的 `skills.tags` 精确过滤，返回符合条件的完整注册内容列表，零 AI 依赖。
- **长期（语义检索）**：对注册内容做向量嵌入，支持 `semantic` 字段查询，Client Agent 描述意图，mq9 返回最匹配的 Agent 列表。

这条路线不破坏现有接口，两个阶段可独立演进。返回体始终是原始注册内容——mq9 存进去什么，返回什么，不转换、不包装。

**几个克制的设计：**

- **最终一致即可，不引入 Raft 等强一致协议**。注册信息变化不频繁，最终一致足够。
- **不做命名空间和租户隔离**。开源版保持简单，企业版可以加。
- **不做 Agent 编排**。找到 Agent、拿到 mailbox 地址，之后的任务分发和协作由应用层决定。
